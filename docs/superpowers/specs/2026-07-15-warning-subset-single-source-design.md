# 预警子集单一源码改造设计

## 背景

`link-warning` 基本是 `link-front` 的功能子集，但当前两个应用仍分别保存大量同路径源码。现有审计显示，`link-warning/src` 的 477 个文件中，470 个在 `link-front/src` 存在同路径文件；其中 323 个内容完全相同，147 个内容已经分叉，另有 7 个只存在于 `link-warning`。

仓库已经将部分预警 API、状态逻辑、报表工具、基础 UI 和一体机选择组件迁入 Workspace 公共包。本次改造延续这一模式，将剩余预警子集逐步收敛到唯一公共实现，同时保持两个宿主应用独立构建和发布。

## 目标

- 预警子集的共同业务主体只保留一份源码。
- `link-warning` 与 `link-front` 共同引用公共实现。
- 两端当前存在的行为差异必须保留，并通过明确的宿主适配器表达。
- 两端原文件路径、路由名称、动态导入路径、Props、事件和 Store 接口保持兼容。
- `build:warning` 与 `build:front` 分别执行，只生成各自产物，互不触发、互不覆盖。
- 改造按 `ForewarningManagement`、公共组件与工具、静态资源三个批次依次完成。

## 非目标

- 不把 `link-warning` 直接作为 `link-front` 的源码依赖。
- 不通过复制或同步脚本继续维护两份公共业务实现。
- 不在共享包中根据应用名称堆叠宿主分支。
- 不在本次改造中统一两个应用本来就不同的产品行为、权限、文案或环境配置。
- 不改变与预警公共化无关的页面和业务模块。

## 总体架构

```text
packages/
├── warning-feature/     # 预警业务逻辑、状态、API、页面组合逻辑
├── shared-ui/           # 无宿主依赖的 Vue 组件
└── shared-core/         # 通用纯函数和基础工具

apps/link-warning/       # 预警版宿主壳
├── src/...              # 原路径薄转发和预警版适配器
├── main.js
├── router/
└── rsbuild.config.js

apps/link-front/         # 完整版宿主壳
├── src/...              # 原路径薄转发和完整版适配器
├── main.js
├── router/
└── rsbuild.config.js
```

共享包不得直接引用 `apps/**`、宿主的 `@/` 别名、宿主 Router 或未经注入的全局 Store。完全相同的实现直接迁入公共包；存在差异的实现拆成共同主体和宿主适配参数；无法合理参数化的差异保留在两个薄包装层中。

## 迁移顺序

### 第一批：ForewarningManagement

迁移 `views/ForewarningManagement` 中剩余的共同页面、组件、状态和业务逻辑。当前该目录在审计中包含 15 个完全相同文件和 34 个分叉文件，是首个完整的垂直业务切片。

- 页面和业务组件进入 `packages/warning-feature/src/forewarning-management/`。
- 无宿主依赖的展示组件进入 `packages/shared-ui/src/forewarning-management/`。
- 状态、筛选、报表和数据转换进入 `packages/warning-feature` 的对应子目录。
- 请求客户端、权限判断、下载能力、环境变量、Router 和宿主 Store 通过适配器注入。
- 图片和图标在第一批继续保留原位置，避免同时改变资源加载行为。

### 第二批：公共组件与工具

迁移 `components` 和 `utils` 中由两个应用共同使用的实现。优先处理完全相同且宿主依赖较少的文件，再处理需要注入环境、请求或权限能力的分叉文件。

### 第三批：静态资源

统一 `icons` 和 `assets` 中的重复资源，建立稳定的公共资源导出或解析方式。该批次不得改变现有资源 URL、哈希策略和部署后的相对路径语义。

## 宿主兼容层

两个应用保留现有文件路径。迁移后的原路径文件只允许承担以下职责：

- 直接再导出共享实现；
- 创建共享实例并注入宿主依赖；
- 包装确实无法公共化的宿主 UI 或行为差异。

分叉文件按以下规则处理：

1. 仅格式、注释或失效代码不同：选择共同实现。
2. 接口地址、权限或环境配置不同：通过适配参数处理。
3. UI 文案、字段或交互不同：通过 Props、Slots、事件或配置对象处理。
4. 页面结构明显不同：共享内部稳定组件和逻辑，两个应用保留各自页面包装层。

适配器必须小而明确。共享包不得读取应用名称后用大段条件分支模拟两个宿主。

## 数据流

```text
宿主原路径文件
    ↓ 注入宿主依赖
共享页面、组件或工厂
    ↓
共享业务逻辑
    ↓ 调用适配接口
请求、权限、Router、Store、下载和环境配置
```

公共实现定义稳定接口，宿主只提供接口所需能力。共享实现的内部调整不得要求调用方重写原路由或动态导入路径。

## 构建隔离

- `pnpm run build:warning` 只构建 `@link/link-warning`，输出到 `dist/link-warning`。
- `pnpm run build:front` 只构建 `@link/link-front`，输出到 `dist/link-front`。
- 两个应用可以编译相同 Workspace 公共包，但不得触发另一个应用的构建命令。
- 两个 Rsbuild 配置继续拥有独立入口、路由组合、环境变量和输出目录。
- 公共包发生变化后，两个应用在各自下一次构建时获得更新；这不等于两个构建产物应当相同。

## 测试与验收

每个迁移批次都采用测试先行：

1. 先增加失败的迁移契约测试，证明目标功能尚未满足单一来源要求。
2. 验证共享包不引用 `apps/**`、`@/` 或未经注入的宿主全局对象。
3. 验证两个应用原路径仍存在，并正确转发或适配共享实现。
4. 为分叉文件分别固定 `link-warning` 和 `link-front` 的当前行为。
5. 运行 `pnpm test`，确保现有迁移、审计和预警功能测试通过。
6. 分别运行 `pnpm run build:warning` 与 `pnpm run build:front`。
7. 更新共享来源审计，确认已迁移功能不再保存两份业务主体。

每一批的完成标准：

- 公共业务主体只有一份；
- 两端现有外部接口和用户行为保持兼容；
- 两端能够独立完成生产构建；
- 构建产物只写入各自目录；
- 全量测试、双构建和共享来源审计均通过。

## 失败处理与回退

- 任一应用构建失败时，不进入下一迁移批次。
- 共享组件无法脱离宿主依赖时，先建立最小适配接口，不允许共享包反向引用应用源码。
- 两端行为无法由同一主体安全表达时，保留两个薄包装层，只共享内部稳定部分。
- 每个垂直切片单独提交并保持可回退，避免全部迁移完成后才暴露集成问题。
- 不在失败修复中扩大到当前批次以外的无关重构。

## 总体完成标准

- `ForewarningManagement`、公共组件与工具、静态资源按顺序完成公共化。
- 已迁移的预警子集功能不存在两份可独立修改的业务主体。
- 两端差异全部位于可识别、可测试的宿主适配层。
- 原路径和现有调用契约保持兼容。
- 两端构建和部署流程互不触发、互不覆盖。
- 仓库测试、独立双构建与共享源码审计提供可重复的验收证据。
